# Vektur Drum — Stage 1 & 2: Source Audit and Extraction Plan

Source audited: the Vektur VJ web build (`index.html`, 15,530 lines, 2.27 MB), dated 2026-11-20.
In Vektur VJ the drum machine is called **Vektur Pulse**. This report covers what it is, how it is built, what it depends on, what is wrong with it, and how it becomes Vektur Drum.

---

## 0. Summary

- **What was audited.** I read every drum-related line in the web build: about 1,400 lines of code plus about 54 KB of generated data. That covers the DSP, sequencer, state, sync, panel, presets and samples. I also traced every point where the drums touch the rest of Vektur VJ.
- **The native code was not available.** The web engine says it is a *"line-for-line port of `native/Shared/DSP/Drums.h` (checked against it by `tools/spectra_parity`)"*. Its parameters and presets are generated by `tools/drumspec.py` and `tools/soundpresets.py`. None of these files were uploaded. For the Xcode project, `Drums.h` is the real extraction source. This audit is complete for the web build and for the behaviour `Drums.h` must match. It is **not** an audit of `Drums.h` itself. → *See §10, item 1.*
- **The drum machine extracts cleanly.** The engine (`drumsMakeEngine`) is pure: it has no DOM, no Vektur VJ state and no allocation after `prepare()`. It already runs headless. Its only coupling is that it is hosted *inside* the Vektur Spectra synth's AudioWorklet and is driven by the VJ's clock, MIDI router and project file.
- **A working standalone extraction exists now.** `reference/web/index.html` is generated by `tools/extract_drums.py`. It copies every drum block from Vektur VJ verbatim, applies 3 documented patches, and adds a 170-line host. It runs without Vektur VJ. This build is the behavioural reference for the native port. 53 headless engine checks pass, and a browser run passes (audio, sequencing, editing, presets, persistence).
- **Two bugs found:**
  1. **Data loss in Vektur VJ.** When a set is reopened, each step keeps only 4 of its 8 fields. Step **crush, delay send, reverb send and chance** are silently reset (§6.1).
  2. **96 kHz.** At a 96 kHz sample rate, every track's sample-and-hold engages even with Rate at maximum, so the drums run at half their sample rate (§6.2).
- **Six tracks are hardcoded in about 25 places** (§5). Moving to 6–9 tracks is a data-layout change, not just a constant: the parameter table, pattern arrays, wire format, telemetry offsets, MIDI note map, hat-choke pairing and UI all assume 6.
- **Many listed features do not exist yet.** These items from the brief are **not** present in Vektur Pulse: attack, release, per-track filters (beyond "tone"), parameter automation or locks, randomisation, MIDI clock, MIDI out, CC learn (except through Vektur VJ's global MIDI-learn), sample start/end/trim, reverse, stereo samples, per-track polyphony, and FM. Per §18 rule 5, each will be marked **NEW** when it is built, never presented as extracted.

## 2. Architecture of Vektur Pulse (as built)

```
 UI thread (DOM)                                   audio thread (AudioWorklet 'vektur-spectra')
 ─────────────────                                 ─────────────────────────────────────────────
 S.drums  (project state: params, 8 patterns,      SpectraProcessor
           chain, samples, user presets)             └─ Spectra synth engine
   │  drumSet / drumPushPattern / drumPushAll             └─ this.drums = new Drums(sr)   ← Vektur Pulse
   │  postMessage({dr:[op,…]})  ───────────────────────►     setParam / setStep / setStepFx / setTrack /
   │  postMessage({m:[st,d1,d2]})  (pads, MIDI)  ──────►     setBars / setChain / select / play / setSample
   │  postMessage({clk:[bpm,beat]})  (VJ clock)  ──────►     setTempo → beat follows host beat
   │                                                       render(L,R,n): per sample
   │                                                         control() every 16 samples (smoothing, caches)
   │                                                         sequence()  (sample-accurate step scheduling)
   │                                                         6 voices → mute/solo → pan → sends
   │                                                         delay (ping-pong) + reverb (Freeverb-style)
   │                                                         warmth → level → DC block → soft clip
   │  ◄───────  {dtel: Float32Array(22), drec: [[p,t,s,vel]…]}  every 4 blocks
 drumsTick() (rAF): LEDs, playhead, OLED — repaint only on change
```

The design is sound and should be preserved:
- **Sequencing runs on the audio thread, sample-accurately.** The UI frame rate never affects timing; I confirmed no drift over 5 minutes (§9).
- **One voice per track.** Each track is monophonic: a retrigger restarts its voice.
- **Parameter smoothing.** Continuous params are smoothed with a one-pole filter (10 ms) at control rate. Discrete params snap.
- **Control-rate caches.** Mute, solo, bits and rate are cached every 16 samples rather than read per sample.
- **Silence skip.** When no voice is active and the effects tail has died, the per-sample work is skipped.
- **Denormal safety.** `ftz()` flushes tiny values to zero in the feedback paths, the DC blocker and the reverb.
- **Pattern changes are quantised.** Selecting a pattern while playing switches at the end of the current pattern. PLAY starts on the next beat.

## 3. Feature inventory (what actually exists)

**Tracks (6, fixed).** There are 15 parameters per track:

| Parameter | Range |
|---|---|
| Model | 8 models, listed below |
| Tune | ±24 st |
| Decay | 10 ms–3 s, log |
| Tone | 0–1 |
| Snap | 0–1 |
| Level | 0–1 |
| Pan | −1 to +1 |
| Bend | ±12 st |
| Bend rate | 0–20 Hz; a sine LFO restarted on each hit, 0 = static bend |
| Bits | 2–16 |
| Rate | 500 Hz–48 kHz sample-and-hold |
| Delay send | 0–1 |
| Reverb send | 0–1 |
| Mute | on/off |
| Solo | on/off |

**Drum models** (analogue-style synthesis):

| # | Model | How it is made |
|---|---|---|
| 0 | Kick | sine 46 Hz × tune, pitch envelope (depth = tone), noise click (snap) |
| 1 | Snare | 185 + 330 Hz sines (body, amp²) + high-passed noise via SVF (900–6900 Hz) |
| 2/3 | Closed / open hat | 6 squares at 808-style metal frequencies + noise → band-pass → high-pass SVF |
| 4 | Clap | band-passed noise, 3 bursts at 10.5 ms spacing + decaying tail |
| 5 | Tom | sine 105 Hz × tune with pitch envelope, noise click |
| 6 | Rim | 1700 Hz sine (amp²) + band-passed noise click |
| 7 | Bell | 587 + 845 Hz squares → resonant band-pass |
| 8 | *Sample* | replaces the model when a sample is loaded on the track |

**Master section:**
- MIDI channel: 0 = any, default 10.
- Swing: 0–0.75. Odd steps are delayed by swing × step ÷ 2.
- Warmth: biased tanh saturation.
- Level.
- Hat choke: track 3 chokes track 4.

**Effects:**
- Delay, tempo-synced to 10 divisions: feedback up to 0.9, tone (one-pole low-pass 800 Hz–16 kHz), ping-pong, 3.05 s buffer.
- Reverb: 8 combs + 4 all-passes per channel, size and damping.
- Output: DC blocker, then a soft clip above 0.8.

**Sequencer:**
- 8 patterns, each 1, 2 or 4 bars.
- Per track, per pattern: length 1–16 steps and division (1/4, 1/4T, 1/8, 1/8T, 1/8., 1/16, 1/16T, 1/16., 1/32, 1/32T). This gives polymeter and polyrhythm.
- Per step: on, velocity, pan, pitch ±12, ratchet ×1–4 (repeats at 0.85 velocity), crush, delay send, reverb send, chance (probability).
- Chain of up to 16 patterns, or loop.
- Quantised pattern switching; start on the next beat.
- **REC**: live pad or MIDI hits are written to the nearest step and sent back to the UI.
- Copy, paste and clear a pattern.
- **Not present:** per-step parameter locks beyond the step fields above, pattern length beyond 16 steps per track, fills, mutes per pattern, song mode.

**Performance:**
- 6 pads. Hit position sets velocity (higher on the pad = harder, 50–127). Space and Enter also trigger.
- MIDI notes 36, 38, 42, 46, 39, 45 → tracks 1–6. Other notes from 36 up wrap around the tracks (see §6.6).
- Note-on only; MIDI velocity is used.

**Samples:**
- WAV or FLAC up to 20 MB, decoded to **mono** at the audio-context rate, capped at 30 s.
- Linear interpolation; pitch follows tune, step pitch and bend.
- Decay envelope: decay ≥ 2.95 s means play to the end. Tone is a one-pole low-pass. Bits, rate and the sends apply.
- Files are deduplicated by an FNV-1a hash and stored inside the project. Unused files are pruned.
- **Not present:** start/end, trim, reverse, stereo, loop, multi-sample, velocity layers.

**Presets:**
- 16 factory kits (House, Techno, Breaks, Hip-hop, Trap, D&B, Dub techno, Electro …). Each kit holds its params, 2 patterns and a chain.
- 16 user slots, saved with the project.
- JSON export/import (`format: "vektur-pulse-presets", version: 1`), with sample files embedded.
- Loading a kit never changes the MIDI channel.

**Telemetry (audio → UI), a 22-float array:**
- running, current pattern, chain position, output level
- per track: current step, hit counter, envelope level

**UI and accessibility (already good):**
- Every step, pad, mute/solo, select and knob has an `aria-label`.
- Knobs are `role="slider"` with `aria-valuenow` and `aria-valuetext`, and arrow keys work.
- Double-tap resets a knob to its default.
- The panel repaints only on change; nothing animates by itself.

## 5. Six-track assumptions (each must change for 6–9 tracks)

The engine and data:
- `kT = 6`; voices, sample slots, `hits`, `ratLeft`, etc. are sized from it.
- `DRUM_PARAMS` is a flat t1…t6 list, with per-track params found by `T1 + t * TSTRIDE`, plus a master block at the end. Adding tracks shifts the master IDs, so the layout has to change.
- `DRUM_NOTES` has 6 notes, and `trackOf()` falls back to `(note − 36) % 6`.
- The hat choke is hardwired to track index 2 → 3, by position rather than by sound.
- Telemetry offsets: `tel[4 + t]`, `[4 + 6 + t]`, `[4 + 12 + t]`; Visual Link reads `dt2[16 + i]`.
- The packed pattern message is `1 + 6 × (2 + 16 × 9)` floats, and the worklet's `'P'` loop has `t < 6`.
- The pattern factories (`drumEmptyPattern`, starter pattern), the load sanitiser, `presetCleanPattern` and `presetClean` (the `smp` array of 6) all build 6 tracks.

The UI:
- `renderDrums` loops over 6 rows and 6 pads, with `lastStep` and `lastHit` sized 6.
- The pad grid is 3 × 2.
- The panel subtitle reads "6-TRACK".

**Design for Vektur Drum:**
- Storage capacity is a compile-time `kTrackCapacity = 16`, so it is never the limiting factor; rule 12 says not to prevent going beyond 9.
- The active track count, 6–9, is a project setting. The sequencer, mixer, telemetry and UI iterate over `activeTracks`.
- Parameter IDs become `trackBase(t) + paramIndex`, with master params in their own fixed ID range, so adding tracks never renumbers anything. This matters because AU parameter addresses must stay stable.
- Default notes for tracks 7–9 (GM): 7 = 49 crash, 8 = 51 ride, 9 = 37 side-stick. These are **NEW** and open to change.
- Choke becomes per-track **choke groups**. This is **NEW**; it replaces the fixed 3→4 pairing, and by default "closed hat chokes open hat" is migrated.

## 6. Issues found

**6.1 Data loss on reopen (Vektur VJ bug).** The set loader (VJ line 8051) rebuilds each step as `[vel, pan, pitch, ratchet]`. It drops crush, delay, reverb and chance. In Vektur VJ today, any step with crush, sends or a chance below 100% is silently reset when the set is reopened. *Vektur Drum:* fixed by loading patterns through `presetCleanPattern`, which keeps all 8 fields; verified across a reload. *Vektur VJ:* not changed (rule 1). A one-line fix is possible if you want it.

**6.2 96 kHz half-rate (both builds).** The per-track Rate maximum is 48 kHz, and sample-and-hold engages when `rate < sr × 0.999`. At 96 kHz every track is therefore held to 48 kHz even at "max": 999 of 2,000 voice samples were repeats in my test. *Fix for the native port:* treat the top of the range as "off", or scale the range to the device rate.

**6.3 Retrigger clicks.** Each track has one voice. A retrigger resets amplitude to 1 and clears phases and filter states instantly, so a long open hat, long kick or sample can click when retriggered (ratchets and fast hats do this a lot). *Native:* 2 voices per track with a ~2 ms fade-out of the outgoing voice.

**6.4 Swing and division change one step late.** The next step's time is computed when the previous step fires, so a swing or division change takes effect one step later. This is musically minor and kept for parity; it is noted in the tests.

**6.5 Hat choke follows position, not sound.** If track 3 is set to a kick, it still chokes track 4. → Replaced by choke groups (§5).

**6.6 Any note on the drum channel plays something.** `trackOf()` maps every note ≥ 36 onto a track (mod 6), which can surprise users of a keyboard on channel 10. → In native, use an explicit note map with unmapped notes ignored. This is an option, not a silent change.

**6.7 Audio-thread allocation (JS-only, but a warning for native).** `recQ.push([…])`, `recQ.splice`, and the object built in `setSample` all allocate on the audio thread. → Native uses a fixed-size SPSC ring for recorded hits and atomic pointer hand-off for sample buffers. Freeing the old buffer happens off the audio thread.

**6.8 Memory and storage.** Samples live in the project as base64 inside JSON (+33%) and as decoded mono floats (≈5.8 MB per 30 s at 48 kHz). The JSON is re-serialised on every edit (400 ms debounce). → Native stores samples as files in a project package, keeps decoded buffers in a cache with reference counts, and keeps project JSON small.

**6.9 Polling.** `setInterval(drumSamplesSync, 1000)` runs forever. → Native replaces it with events.

**6.10 Tempo is external.** Vektur Pulse has no tempo of its own; it follows the VJ clock, and the `hostBeat` correction pulls its beat toward the VJ's. → An internal clock was added to the extraction (TEMPO knob). Native also needs MIDI clock in, an AU host musical context, and later Ableton Link.

## 8. Proposed standalone architecture (Stage 3 starting point)

**DSP in C++, everything else in Swift.**
`Drums.h` already exists natively and is parity-checked against this JS, so the native engine is extraction, not a rewrite. The render loop needs hard real-time guarantees: no ARC traffic, no allocation, no exclusivity checks, no locks. C++ gives those plainly, and it is the language an AUv3 render block expects. Swift owns the app, the models, persistence and the UI.

The bridge is a small **C API facade** (`vd_engine_*`) over the C++ engine rather than full Swift/C++ interop. The facade is stable and easy to call from an `AUInternalRenderBlock`. It keeps C++ types out of Swift, and it means the interop setting is not part of every target.

**Audio host: an `AUAudioUnit` from day one.**
The engine lives in a `VekturDrumAudioUnit` (instrument, `aumu`). The standalone app loads it in-process into **AVAudioEngine** (`AVAudioUnit.instantiate`) and connects it to the main mixer. The future AUv3 extension then reuses exactly the same unit, so "standalone vs AUv3" is a packaging choice, not a second engine.

I rejected `AVAudioSourceNode`. It is simpler, but it would have to be redone for AUv3, and it has no parameter tree, so no automation. If you'd rather start simpler, it remains a valid choice.

**Threads and communication.**

UI → audio:
- **Parameters:** `AUParameterTree`, so they are automatable, host-visible and smoothed in the engine as today.
- **Structural commands** (step edits, pattern writes, track count, chain, transport, sample hand-off): a fixed-size lock-free SPSC command ring of POD structs.
- **Sample buffers:** allocated off the audio thread and handed over by atomic pointer. The old buffer goes back through a release ring and is freed off the audio thread.

Audio → UI:
- **Telemetry:** an atomic snapshot written once per block and read by the UI at display rate, only while the panel is visible.
- **Recorded hits:** an SPSC ring.

**Clock.** The sequencer stays sample-accurate inside render, as today. The beat source is one of:
- the internal clock (standalone);
- the host's `musicalContextBlock` / `transportStateBlock` (AUv3);
- MIDI clock (NEW);
- Ableton Link (future).

The `hostBeat` correction already in the engine is the hook for all of these.

**Track and voice model.**
- Each track has an **engine** (`analog` = the 8 existing models, `sample`, `fm`) plus the shared per-track channel: level, pan, mute, solo, bits, rate, sends, choke group.
- Voices are a tagged variant per track, chosen with a `switch` on the hot path (no virtual calls), with 2 voices per track for declicked retrigger.
- The FM engine (Stage 7) plugs in as a third voice type with its own parameter block. The sequencer never needs to know which engine a track uses.

**Suggested modules** (Swift packages / targets, not hundreds of files):

| Module | Language | Contents |
|---|---|---|
| `VekturDrumDSP` | C++ (+ C header) | `Drums.h` port, voices (analogue, sample, FM later), sequencer, effects, mixer, command queue, telemetry; unit-testable headless |
| `VekturDrumAudio` | Swift | `VekturDrumAudioUnit`, `AudioEngineController` (AVAudioSession, AVAudioEngine, interruptions, route and sample-rate changes), `MIDIManager` (CoreMIDI) |
| `VekturDrumCore` | Swift | Project model (Codable), patterns, kits, `PresetManager` (incl. `vektur-pulse-presets` import), `ProjectManager` / persistence, sample library (AVAudioFile decode off-thread) |
| App | SwiftUI | `DrumMachineView`, `SequencerView`, `TrackView`, `PadsView`, `SoundView`, `StepView`, `FMEditorView`, `MixerView`, `SettingsView`, the `Knob` control |

**SwiftUI notes.**
- UI state uses `@Observable` models, and audio state never lives in views.
- The step grid is driven by equatable row views. The moving playhead is a separate overlay layer, so the whole grid is not recomputed each frame.
- Knobs are drawn with `Canvas`, matching the existing knob: 270° sweep, value arc, bipolar from the centre, drag up/down, double-tap to default, VoiceOver adjustable.
- The visual identity (graphite chassis, brushed-aluminium top strip, amber LEDs, cyan OLED and selection) is captured from the extracted CSS as design tokens.

## 9. Testing status

Tests run against the extracted engine (`tests/engine.test.js`, Node, offline render at 48 kHz): **53 checks pass.** These include:
- all 8 models are finite, bounded and audible;
- quarter-note kicks land within 2 blocks of the beat grid;
- **zero drift over 5 minutes at 133 BPM**;
- swing timing;
- mute and solo;
- chance 0 is silent and ratchet ×4 gives 4 hits;
- polymeter (a 3-step track);
- chain advance;
- hat choke;
- MIDI channel and note map;
- REC queue;
- a 20-second delay + reverb stress test (finite, bounded, no DC, tail dies away);
- sample playback stopping at its end;
- 44.1/48/96 kHz tempo accuracy.

JS render cost: about 25× real time with 6 tracks of 16ths plus effects (informational).

Browser test (headless Chrome, `reference/web/index.html`):
- the worklet starts, PLAY runs and the LEDs track the playhead;
- step toggle works;
- a factory kit loads;
- tempo and pattern edits survive a reload;
- no console errors.

**These tests become the parity suite.** The native `VekturDrumDSP` must render the same output as the JS engine for the same inputs, as `tools/spectra_parity` already does for Vektur VJ. Native-only tests to add:
- an allocation and lock audit of the render path;
- a long-run soak (hours) on device;
- interruption, route-change and sample-rate-change tests;
- CPU at the 64-frame (≈1.3 ms) buffer on the oldest supported iPad.
